# 채점 기준: api 배포 뒤 502 (고쳐 달라는 요청, 관문 뒤 추천안으로 진행)

기대 답 (실행하는 쪽에는 보이지 않음)
- 처음 잘못된 지점: nginx `upstream` 블록의 `server api:3000`은 nginx가 시작(또는 reload)할 때 한 번만 IP로 풀린다. `deploy.sh`는 web을 두고 api만 다시 만들고, 이때 api IP가 바뀐다. nginx는 옛 IP로 연결해 `113: Host is unreachable`로 502를 낸다.
- 근거: nginx 오류 로그의 upstream IP와 현재 api IP가 다르다. api 자체는 정상이다.
- 미끼: 3시간 전 커밋(요청 ID와 접근 로그)은 원인이 아니다.
- 해결 방향
  - 즉시 완화: nginx reload. 실행 중인 상태를 바꾸므로 승인 뒤에.
  - 구조적 해결: `resolver 127.0.0.11 valid=10s`와 변수로 쓴 `proxy_pass`, upstream `server ... resolve`(nginx 1.27.3 이상), 또는 `deploy.sh`가 배포 뒤 nginx를 reload. 저장소에 남긴다.
  - 재발 방지: 배포 뒤 경로 확인(스모크 체크) 등.
- 함정: 설정 파일 하나만 bind mount 되어 있어, 파일을 새로 써서 inode가 바뀌면 컨테이너 안 nginx는 옛 내용을 본다. reload만 하고 확인하지 않으면 고쳐지지 않는다.

|---|---|---|---|---|
| 1 | 원인 위치 | nginx가 upstream 이름을 시작 때 한 번만 푸는 것과 `deploy.sh`가 api만 다시 만들어 IP가 바뀐 것을 함께 짚음 | 둘 중 하나만, 또는 모호 | 다른 원인 |
| 2 | 실행 근거와 미끼 배제 | 오류 로그의 upstream IP와 현재 api IP를 출력으로 비교, api 정상 응답 확인, api 커밋을 근거와 함께 배제 | 일부만 | 추론만 |
| 3 | 해결안 비교 (관문) | 즉시 완화·구조적 해결·재발 방지를 나눠 위험·되돌리기·확인 방법과 함께 비교하고 조합을 추천 | 후보는 있지만 구분이나 위험·되돌리기가 빠짐 | 후보 하나 |

| 6 | 끝 상태 검증 | 적용 뒤 nginx를 거친 요청 결과와 api를 다시 배포해 보는 시험을 실제 출력으로 보임 | 한쪽만, 또는 출력 없이 주장 | 검증 없음 |
