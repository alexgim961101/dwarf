# 요약 먼저 (summary first)

- 언제: 최종 답변·보고를 쓰기 전. 문서로 남기기 전.
- 규칙: 핵심은 빠뜨리지 않고, 핵심마다 설명은 짧게 쓴다. 더 깊은 설명은 사용자가 물을 때 한다.
- 왜: 설명이 길면 핵심이 묻히고 끝까지 읽히지 않는다. 무엇을 더 알고 싶은지는 사용자가 가장 잘 알고, 질문을 받아 그 부분만 풀어 쓰는 편이 전부 미리 쓰는 것보다 빠르다.
- 방법:
  - 쓰기 전에 핵심을 고른다. 결론, 근거, 결론을 이해하는 데 필요한 배경, 남은 위험과 미확인. 이것들은 줄이지 않는다.
  - 핵심마다 한두 줄. 같은 말을 바꿔 반복하거나 과정을 단계마다 서술하지 않는다. 비교·수치는 표로 줄인다.
  - 길게 풀 수 있는 부분은 한 줄로 두고, 사용자가 물으면 그때 풀어 쓴다.
  - leaf·위임 결과는 재료다. 출력을 그대로 붙이지 않고 핵심만 옮긴다.
  - 문서도 같다.
  - 용어와 이름. 처음 나오는 용어(통계·도구 용어, 약어)는 한 줄로 풀고 구체적인 값 예시를 단다. 구간·지표 이름은 그 안에서 실제로 일어나는 일로 짓는다("빈 시간" 대신 "받은 묶음 처리"). 그림은 축·위치·색이 모두 뜻을 갖고 축 이름으로 읽혀야 한다.
  - 다른 사람이 읽을 곳(이슈·PR·위키)에 쓰면 독자는 작업을 보지 않았다. 내 머신의 경로·측정 스크립트 이름을 빼고, 방법은 짧게, 비교표와 원시 데이터로 만든 그림을 증거로 둔다. 작업 과정·정정 이력은 넣지 않는다. 미확인 목록은 결론을 바꿀 수 있는 것만 남기고 본문의 추정 표시는 그대로 둔다.
- 아닌 것:
  - 글의 구조나 순서를 바꾸는 것. playbook 보고 형식과 문서 구조는 그대로 따르고, 각 부분의 설명 길이만 줄인다.
  - 핵심을 빼서 짧게 만드는 것. 판정을 받치는 출력은 원문으로 붙이고(`p-prove-it-works`), 추정·미확인 표시는 줄이지 않는다.
  - 이름을 줄이는 것. API 경로·함수·파일 경로·토픽 같은 식별자는 길어도 원문 그대로 쓴다. 짧게 하는 것은 설명이다.
  - 결정을 사용자에게 넘기는 질문. 질문을 받는다는 것은 사용자가 더 물을 수 있게 두는 것이다(`p-act-before-asking`).
