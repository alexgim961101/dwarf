# 동작을 테스트 (test behavior)

- 언제: 테스트를 쓰거나 바꾸거나 지울 때. 리팩터링 전 안전망을 만들 때.
- 규칙: 코드 사용자가 관찰할 수 있는 것을 단언한다. 그 동작이 깨지면 실패하고, 내부만 바뀌면 계속 통과해야 한다.
- 왜: 구현을 단언하는 테스트는 리팩터링마다 깨져서 고치는 비용만 들고, 실제 결함은 잡지 못한다.
- 방법:
  - 입력과 관찰 가능한 출력(반환값, 저장된 상태, 호출된 외부 효과)으로 테스트를 쓴다. 내부 함수 호출 순서나 private 상태를 단언하지 않는다.
  - 리팩터링 전에는 현재 동작을 그대로 고정하는 테스트를 먼저 추가한다. 이 테스트는 리팩터링 뒤에도 바뀌지 않아야 한다.
  - mock은 경계(네트워크, 시간, 파일)에만 둔다. 내부 협력 객체를 mock하면 구현을 단언하게 된다.
  - 테스트 이름은 동작을 문장으로 적는다. 함수 이름을 반복하지 않는다.
  - 결함 수정은 실패하는 테스트를 먼저 쓰고 실행해 의도한 이유로 실패하는지 본다. 통과하거나 다른 이유로 실패하면 테스트부터 고친다.
  - 테스트가 넓은 harness, 느린 인프라, mock 위주를 요구하면 만들지 않는다. 나쁜 테스트보다 테스트 없음이 낫다. 가장 가까운 실행 가능한 확인(스크립트, 재현 명령, 로그 단언)으로 대신하고 그렇게 했다고 적는다.
  - 틀린 구현에 맞추려고 테스트를 고치거나 단언을 약화하지 않는다.
- 아닌 것: 테스트 수를 늘리는 것이 목표가 아니다. 같은 동작을 다른 경로로 반복 단언하는 테스트는 지운다.
