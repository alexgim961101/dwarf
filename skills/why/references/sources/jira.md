# Jira (Atlassian MCP)

제품·업무 맥락이 사는 곳. "고객 X가 요청해서", "Q3 규정 대응이라서" 같은 층은 코드가 아니라 여기 있다.

## 전제

- 세션에 `mcp__atlassian__*` 도구가 보일 때만 조사한다. 없으면 이 출처는 "공백. Jira 도구 없음"으로 기록하고 추측으로 채우지 않는다.
- 읽기 도구만 쓴다. 이슈 수정, 상태 전이, 댓글 작성, 이슈 생성 도구가 같은 서버에 있으므로 호출하지 않는다.
- 도구 이름은 세션 목록에서 확인한다. Atlassian 공식 MCP 기준 예시는 이슈 조회 `getJiraIssue`, JQL 검색 `searchJiraIssuesUsingJql`, 원격 링크 `getJiraIssueRemoteIssueLinks`. 이름이 다르면 같은 기능의 도구를 쓴다.

## 무엇이 있나

- 이슈 본문. 문제 설명, 수용 기준, 배경.
- 댓글. 범위 변경, 결정 기록, "왜 이렇게 하기로 했는지".
- Epic·부모 이슈와 서브태스크. 서브태스크는 전술, Epic이 "왜"를 들고 있는 경우가 많다.
- 링크된 이슈. relates to, blocks, duplicates, caused by.
- 라벨, 컴포넌트, 우선순위, 수정 버전. 동기의 종류를 가리킨다.
- 상태 전이 이력. 재오픈, 보류, 범위 축소의 시점.
- 첨부와 연결된 PR·브랜치.

## 어떻게 찾나

1. 앵커의 이슈 키부터 조회한다. 커밋·PR·브랜치명의 `UCNT-1234` 같은 키. 본문과 댓글을 전부 읽는다.
2. 키워드로 JQL 검색한다. 기능 이름, 핵심 심볼, 업무 용어로 여러 표현을 시도한다. 예: `project = UCNT AND text ~ "<키워드>" ORDER BY created DESC`. 프로젝트 키는 앵커의 이슈 키에서 가져온다.
3. 이슈 트리를 오른다. 서브태스크에 도착했으면 부모와 Epic을 읽는다.
4. 링크된 이슈를 따라간다. duplicates 체인은 원본까지.
5. 댓글의 결정 문장과 상태 전이의 시점을 코드의 변경 날짜와 맞춰 본다.

## 좋은 증거

- 본문의 업무 문제 서술. "매장 A에서 카운트가 두 배로 집계돼 정산이 틀림."
- 댓글의 결정 기록. "B안으로 간다. A안은 결제 서비스를 건드려야 해서."
- Epic 제목이 이니셔티브인 것. "정산 정확도 개선", "파노라마 카메라 도입".
- 첨부된 요구 문서나 화면.
- 라벨. `customer-request`, `incident`, `perf`, `regression`.

## 함정

- 템플릿 보일러플레이트. "사용자 경험 개선" 같은 일반 문구는 이유가 아니다.
- 오래된 이슈는 바뀐 계획을 담고 있다. 날짜를 코드의 변경 날짜와 대조한다.
- 범위 이동. PR이 참조한 이슈가 닫히고 다른 범위로 다시 열렸을 수 있다. 전체 이력을 읽는다.
- 권한이 없어 열 수 없는 이슈는 공백으로 기록한다. 추측하지 않는다.
- 이슈 키 없는 커밋은 JQL 키워드 검색으로만 찾을 수 있고, 못 찾으면 공백이다.

## 반환

이슈마다 키와 제목, 문제·동기의 원문 인용(요약 금지. owner가 그대로 인용한다), 라벨·Epic·상태, 작성자·생성일·종료일, URL. 연결된 PR·브랜치는 소스 관리 출처의 단서로.
