# why

코드가 왜 이 모양인지 답한다. 출처마다 조사하고, 찾은 것과 추론한 것을 등급으로 구분한다. 코드 변경 없음.

## 절차

1. 앵커를 만든다. 대상 파일·줄 범위·심볼, `git blame -L`의 마지막 커밋들, `git log --follow`, 커밋 제목의 PR 번호(`(#1234)`), 커밋·PR 본문의 이슈 키. 명령은 `references/sources/source-control.md`. 이 앵커를 모든 investigator와 종합에 같은 내용으로 준다.
2. 출처를 열거한다. 세션에 보이는 도구로 판단한다.

   | 출처 | 조건 | playbook |
   |---|---|---|
   | 소스 관리. git 이력, `gh` PR·리뷰, 주석, 테스트, ADR | 항상. 유일하게 보장된 출처 | `references/sources/source-control.md` |
   | Jira | `mcp__atlassian__*` 도구가 보일 때 | `references/sources/jira.md` |
   | 문서·위키, 채팅, 관측(로그·대시보드) | 해당 `mcp__<server>__*` 도구가 보일 때 | 없음. brief의 일반 지시만으로 조사 |
   | 코드 자체. 마이그레이션, 설정 변경, 같은 시기의 인접 변경 | 소스 관리 investigator가 함께 본다 | source-control.md에 포함 |

   같은 종류의 출처가 두 번 필요해지면 playbook을 추가한다.
3. 출처별로 조사한다. 위임 여부와 Agent는 `../dwarf/references/roles.md`의 "위임 여부와 Agent"를 따른다.
   - 위임. 출처마다 explorer 하나를 `references/investigator-brief.md`로 동시에 보낸다. 앵커를 채우고 그 출처의 playbook을 끝에 붙인다. 한 explorer에 출처 둘을 맡기지 않는다. brief 첫 줄 "읽기만 한다"는 MCP 도구가 쓰기를 할 수 있으므로 빼지 않는다.
   - 직접. owner가 같은 brief 순서로 소스 관리부터 직접 조사한다.
4. owner가 종합한다. 보고를 그대로 붙이지 않는다. 인용은 원문을 열어 한 번 더 확인한다.
5. 주장마다 등급을 붙인다.

| 등급 | 기준 |
|---|---|
| 직접 | PR 본문·이슈·커밋 메시지·주석에 이유가 원문으로 있음. 인용 첨부 |
| 뒷받침 | 원문은 없지만 독립된 간접 근거 둘 이상이 같은 방향 |
| 추론 | 코드 모양·변경 시점·인접 변경에서 유도. 근거를 적되 사실로 쓰지 않음 |
| 추측 | 근거 없음. 가설로만 |
| 미확인 | 찾아봤지만 아무 출처에도 없음. 어디를 봤는지 적음 |

## 출력 형식

- **질문.** 한 문장.
- **대상 코드.** 파일:줄, 심볼, 도입 커밋과 PR.
- **발견한 것.** 직접·뒷받침 등급. 출처와 인용.
- **추론할 수 있는 것.** 추론 등급. 근거.
- **경쟁 가설.** 둘 이상이 남으면 각각의 근거와 반증 방법.
- **모르는 것.** 미확인. 어디를 봤는지.
- **조사한 출처.** 출처별로 봤는지, 무엇을 찾았는지.
- **신뢰도 요약.** 핵심 답 한 문장과 그 등급.

## 경계

- 동작 설명은 `how`. 동기 조사 중 동작이 먼저 필요하면 how를 먼저 돌린다.
- 전제가 틀렸으면(그 코드가 그런 이유로 있지 않음) 그렇게 말한다. 사용자의 가설에 맞춰 근거를 고르지 않는다.
