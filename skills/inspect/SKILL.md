# inspect

변경이 의도대로인지 판정한다. 산출물은 근거가 붙은 발견 사항과 판정. 파일은 수정하지 않는다.

## 입력

- 변경. base와 브랜치, 커밋 범위, PR 번호, 또는 `git diff <base>` 명령.
- 의도. 변경 목적과 완료 기준 한 문장. 없으면 PR 설명·커밋 메시지에서 만들고, 코드에서 추론했으면 추론이라고 표시한다.
- 선택. 중심 질문. 이 변경에서 특히 확인할 것. 예: "관찰 가능한 동작이 바뀌었나".

## 절차

1. 변경 범위를 잡는다. 변경 파일 목록, diff, 닿는 호출부. 변경이 닿는 서브시스템을 모르면 `how`.
2. 의도와 대조한다. 중심 질문이 있으면 먼저 답하고 아래 목록을 차례로 본다.
   - 의도와 다른 동작.
   - 회귀 가능성. diff 밖에서 깨질 수 있으면 `blast-radius`로 안전의 근거를 증명한다.
   - 빠진 검증. 바뀐 동작을 덮는 테스트·확인 명령이 있나.
   - 요구에 없는 변경, 불필요한 추가(`p-necessary-only`).
   - 구조 위반. 계층·의존 방향·공개 계약, 같은 역할의 두 번째 경로(`p-respect-structure`).
   - 설명 없는 주석, 주석 처리된 코드, 우회를 설명하는 주석. 권고 항목.
3. 발견 사항마다 위치(파일:줄), 문제, 근거 또는 재현, 심각도를 적는다. 실행으로 확인할 수 있으면 실행한다(`p-prove-it-works`). 심각도는 차단(머지하면 의도와 다르게 동작하거나 회귀가 생김) / 권고 / 참고.
4. 독립 리뷰. 위임 여부와 Agent는 `../dwarf/references/roles.md`의 "위임 여부와 Agent"를 따른다.
   - 위임. 같은 변경·의도·중심 질문을 같은 파일의 reviewer brief로 보낸다. 받은 발견 사항은 직접 확인하고 owner의 것과 일치·불일치를 표시한다.
   - 직접. "독립 리뷰 없음"으로 적는다. 2~3단계의 owner 점검이 체크리스트 재검토를 대신한다.
5. 판정한다. 차단이 하나라도 있으면 수정 필요. `git status`로 변경이 없는지 본다.

## 출력 형식

- **의도.** 한 문장. 추론이면 표시.
- **중심 질문의 답.** 있을 때. 근거와 함께.
- **발견 사항.** 표. 위치, 문제, 근거, 심각도.
- **확인했고 문제없던 항목.** 무엇을 봤고 왜 괜찮은지.
- **독립 리뷰.** 일치·불일치, 또는 "독립 리뷰 없음".
- **판정.** 머지 가능 / 수정 필요.

## 경계

- 파일을 수정하지 않는다. 차단 항목을 고치는 일은 부르는 쪽 몫.
- 동작 설명은 `how`, 기존 설계의 동기는 `why`.
