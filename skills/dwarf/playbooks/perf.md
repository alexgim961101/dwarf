### Perf

동작은 그대로 두고 빠르거나 가볍게 만든다. 모든 수정은 측정에 묶인다. 소스를 읽고 짐작하는 대신 측정한다.

1. 증상을 지표로 바꾼다. p95 ms, req/s, 작업 완료 시간, 최대 RSS 중 하나와 데이터셋 크기. 단위는 여기서 정하고 보고까지 바꾸지 않는다(`p-unify-units`). 비교 기준을 정한다. "느려졌다"면 정상이던 버전·커밋이 기준이고 목표치는 그 수준이다. 그 밖에는 목표치가 기준이다. 목표가 없으면 현재값 기준 상대 목표를 사용자와 정한다.
2. `bench` 스킬로 측정 환경을 준비한다. 서비스 모드인지 작업 모드인지 정한다. 프로젝트에 없으면 템플릿에서 만든다.
3. 재현과 기준선. 변경 전 코드로 5회, 중앙값·범위. 기준이 정상 버전이면 그 버전과 번갈아 재고, 범위가 겹치지 않아야 재현이다. 재현되지 않으면 시도한 조건을 남기고 멈춰 보고한다. 보고하지 않는 run에서 프로파일을 받아 limiter를 지목한다(`p-explain-the-number`). limiter 없이 4단계로 가지 않는다.
4. 원인 파악. 코드 밖 원인(설정·데이터·인프라·런타임 버전)부터 배제한다. `how` 스킬로 경로를 잡고 프로파일 핫스팟을 소스에 대응시킨다. 회귀이고 의심 커밋이 많으면 별도 worktree에서 `bench` 측정을 판정으로 `git bisect`한다. 원인은 처음 잘못된 지점(파일:줄 또는 커밋)과 메커니즘으로 적는다. 가설은 비용 낮은 순서로 세운다. 안 한다 → 한 번만 한다 → 덜 한다 → 나중에 한다 → 병렬로 한다 → 싸게 한다. 앞 단계가 목표를 채우면 멈춘다.
5. 원인 제거 실험. 별도 worktree에서 원인만 되돌리거나 끄고, 정상 버전(있으면)·현재·원인 제거를 `bench`로 같은 조건에서 번갈아 5회 잰다. 사용자의 작업 트리는 건드리지 않고 끝나면 worktree를 지운다. 늘어난 시간의 일부만 회복되면 원인이 더 있다. 4단계로 돌아가거나 미확인으로 남긴다. 6단계 수정이 이 제거와 같으면 `skip: 이유`.
6. 수정. 한 번에 가설 하나(`p-verifiable-units`). 함수 경계를 넘으면 대안을 둘 이상 적고 고른 이유를 남긴다. worker 매핑이 있으면 worker brief로 위임하고 diff를 직접 읽는다.
7. 사후 측정. 같은 환경·데이터·스크립트로 번갈아 5회. 오류 수와 처리 건수를 확인한다. 일이 측정 구간 안에서 실제로 일어났는지.
8. 숫자 설명. limiter, 한계 산술, 오류 0, 재현성. 결론은 빨라짐 / 느려짐 / 차이 없음 / 불확정 중 하나(`p-explain-the-number`). 불확정이면 그렇게 말한다.
9. 리뷰. `inspect` 스킬로 점검하고 차단 항목을 처리한다. 의도는 1단계 지표와 목표치, 중심 질문은 "이 숫자가 측정하려던 것을 측정했나". 커밋 준비. 아티팩트 경로를 커밋 본문에 둔다.

목표 지표를 향한 여러 라운드의 지속 개선은 범위 밖. 동작이 바뀌어야 빨라진다면 멈추고 feature를 제안한다.

**멈춤:** 5단계 뒤. 보고는 아래 형식에서 "수정과 사후 측정"을 뺀 것. 이어 가면 6단계부터.

**보고:** 아래 형식으로 `<작업 디렉토리>/.docs/perf/<날짜>-<주제>/report.md`에 쓰고, 답변에는 개요, 비교표, 문서의 절대 경로를 준다. `<날짜>`는 `YYYY-MM-DD`, `<주제>`는 영문 kebab-case. 작업 디렉토리는 세션을 시작한 디렉토리이고 `bench` 아티팩트와 같은 곳이다. 해당 없는 절은 뺀다. 측정 출력은 원문으로 붙인다. 그래프·스크린샷은 UI 성능이거나 사용자가 요청할 때만.

```markdown
# <무엇이 느린가>

## 개요
- 상황: 무엇이, 언제부터, 얼마나. 지표와 수치
- 결론: 원인 한 줄. 원인 제거 또는 수정 뒤 회복 정도 한 줄. 빨라짐 / 느려짐 / 차이 없음 / 불확정

## 재현 방법
- 환경: 버전·커밋, 데이터셋 크기, 머신(`nproc`, 부하)
- 명령: 다시 돌릴 수 있는 명령, 아티팩트 경로
- 결과: 기준 vs 현재. 중앙값, 범위, 횟수

## 원인 분석
| 가설 | 확인 방법 | 결과 |
|---|---|---|
| <가설> | <명령·관측> | <지움 / 남음과 근거> |

- 원인: 처음 잘못된 지점(파일:줄 또는 커밋), 메커니즘, limiter, 증거(프로파일·쿼리 수 등)

## 기존 성능과 원인 제거 후 성능
- 제거 방법: 무엇을 어떻게 임시로 뺐나. worktree를 지웠는지

| | 기준 | 현재 | 원인 제거 |
|---|---|---|---|
| 중앙값 | | | |
| 범위 | | | |
| 횟수 | | | |
| 오류 수 | | | |

- 해석: 늘어난 시간 중 몇 %를 설명하나, 남은 차이. 기준이 목표치면 기준 열에 목표치

## 수정 방향
<멈췄을 때. 제거 실험은 수정이 아니다. 영구 수정 대안 1~2개>

## 수정과 사후 측정
<끝까지 갔을 때. 무엇을 바꿨나, 기준선 → 사후(중앙값, 범위, 횟수), 오류 수와 처리 건수>

## 확인하지 못한 것
- <추정·미확인. 예: 운영과 로컬의 데이터 규모 차이>
```
