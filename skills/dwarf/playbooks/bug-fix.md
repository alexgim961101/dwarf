### Bug fix

결함을 원인이 있는 곳에서 고친다. 바꾼 줄마다 실행해서 얻은 증거로 이유를 댈 수 있어야 한다. "혹시 도움이 될까" 싶어 넣는 방어 코드는 아직 가설이므로 넣지 않는다. 해결안은 글로만 정하지 않는다. 시험해 본 결과를 보고하고, 사용자가 고른 해결안으로 고친다.

1. 원인: `root-cause` 스킬로 재현하고, 문제가 처음 시작된 곳과 결함이 생기는 과정을 확정한다. 상태가 "확정"이 아니면 해결안으로 넘어가지 않고 여기서 멈춰 결과를 보고한다.
2. 해결안 후보: 문제가 처음 시작된 곳을 고치는 후보를 세운다(`p-fix-root-causes`). 상태와 분기가 얽혀 있으면 데이터 형태부터 정한다(`p-model-the-domain`). 후보마다 증거가 뒷받침하는 범위에서 가장 작게 고친다. 고칠 방법이 하나뿐이면 후보도 하나지만, 변경이 함수 하나 안에서 끝나지 않으면 후보를 둘 이상 세운다. 후보는 세 개까지. 1단계에서 같은 결함이 있는 다른 곳을 찾았으면, 후보마다 그곳도 함께 고치는지 적는다.
3. 해결안 시험: 후보마다 별도 worktree를 만들어 적용하고, 1단계의 재현 명령과 바뀐 코드에 닿는 기존 테스트를 실행한다. 사용자의 작업 트리는 건드리지 않는다.
   - 후보가 둘 이상이고 worker 매핑이 있으면 후보마다 worker를 하나씩 붙여 한 메시지에 동시에 띄운다. worker brief의 범위는 그 worktree 안의 파일, 목표는 그 후보를 적용한 뒤 재현 명령에서 버그가 더는 나타나지 않는지 확인하는 것, 확정된 사실은 1단계 원인, 완료 기준은 재현 명령과 기존 테스트, 커밋은 금지다.
   - worker 매핑이 없거나 후보가 하나면 owner가 하나씩 시험한다.
   - 시험끼리 포트, DB, 컨테이너를 함께 쓰면 동시에 돌리지 않고 하나씩 시험한다.
   - 결과는 owner가 worktree의 diff와 출력 원문으로 직접 확인한다. 확인이 끝나면 diff와 출력을 보고에 옮기고 worktree를 지운다.
4. 관문 1: 사용자 승인을 기다린다. 아래 보고 형식에서 관문 1에 쓰는 내용으로 보고한다. 적용한 뒤에도 재현 명령에서 버그가 나타나는 후보는 추천하지 않는다. 모든 후보에서 버그가 그대로 나타나면 원인 판단이 틀렸을 수 있으니 1단계로 한 번 돌아가 원인을 다시 확인하고 2~3단계를 다시 한다. 그래도 모두 실패하면 그 결과를 보고한다. 사용자가 해결안을 고르면 그 해결안으로 5단계에 간다.
5. 구현: 고른 해결안을 작업 트리에 적용한다. 실패하는 테스트부터 쓴다(`p-verifiable-units`, `p-test-behavior`). 테스트를 만들기 너무 비싸거나 무엇을 테스트할지 불분명하면 `skip: 이유`를 적고 대신 확인할 방법을 정한다. worker 매핑이 있으면 worker brief로 맡기고 돌아온 diff를 직접 읽는다. 없으면 owner가 직접 구현한다.
6. 검증: 1단계의 재현 명령을 증상이 나타났던 곳에서 다시 실행해 버그가 더는 나타나지 않는지 확인한다. 단위 테스트가 통과했다고 결함이 없어졌다고 말하지 않는다. "확인할 수 없음"은 통과가 아니다(`p-prove-it-works`). 버그가 여전히 나타나면 5단계 변경을 되돌리고, 1단계로 돌아가 원인을 다시 확인한 뒤 관문 1에서 다시 보고한다. 같은 결함에서 두 번째로 실패하면 더 고치지 않고 멈춰, 두 시도와 실패 출력, 두 시도가 함께 기댄 가정을 보고한다.
7. 리뷰: `inspect` 스킬로 점검하고 차단 항목을 해결한다. 이때 넘기는 의도는 "1단계의 결함은 고쳐지고 다른 동작은 그대로다".
8. 커밋 준비: 실패하는 테스트가 수정보다 먼저 오도록 커밋 순서를 잡는다. 커밋은 사용자가 요청할 때만 한다.

**멈춤:** 관문 1에서 멈춘다. 멈춤 요청이면 승인을 기다리지 않고 관문 1 보고로 마친다. 1단계 상태가 "확정"이 아니면 2~4단계를 건너뛰고 1단계 결과를 보고한다. 이어서 진행하면 고른 해결안으로 5단계부터 한다.

**보고:** 아래 형식으로 답한다. 관문 1 보고도 같은 형식이고, 절 이름 옆 표시대로 관문 1과 최종 보고에 쓰는 내용이 다르다. 문서 전체를 이 프로젝트 코드를 모르는 개발자가 읽어도 흐름을 이해할 수 있게 쓴다. 함수·변수 이름 대신 하는 일로 설명하고, 파일:줄과 출력 원문은 근거와 검증에만 둔다. 해당 없는 절은 뺀다. 사용자가 요청하면 `<작업 디렉토리>/.docs/bug-fix/<날짜>-<주제>/report.md`에도 쓴다. `<날짜>`는 `YYYY-MM-DD`, `<주제>`는 영문 kebab-case, 작업 디렉토리는 세션을 시작한 디렉토리다.

```markdown
# 개요
- 어떤 상황에서 어떤 문제가 발견되었는지
- 영향: 누가, 얼마나 자주 겪는지. 알 수 있을 때만

# 재현
- 조건과 명령, 결과. 가끔만 일어나면 몇 번 중 몇 번인지

# 원인
- 결함이 생기는 흐름
- 근거: 문제가 처음 시작된 곳(파일:줄), 핵심 출력 한두 줄
- 같은 결함이 있는 다른 곳: 있을 때만

# 해결 방법
- 관문 1: 후보 비교표와 추천
  | 후보 | 무엇을 바꾸나 | 적용 뒤 버그 | 기존 테스트 | 장점 | 단점·위험 | 영향 범위 |
  - 추천: 어느 후보인지와 이유
- 최종: 고른 해결안과 이유, 실제로 바꾼 내용

# 검증 (최종만)
- 재현 명령의 수정 전후 출력 원문(버그가 나타나던 출력과 더는 나타나지 않는 출력), 기존 테스트 결과, 리뷰 결과

# 확인하지 못한 것
- 결론을 바꿀 수 있는 것만

# 결정할 것 (관문 1만)
- 예: "후보 A로 진행할까요?"
```
