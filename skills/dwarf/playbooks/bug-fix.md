### Bug fix

작업을 소유한다. 모든 변경 줄은 런타임 증거로 설명된다. "도움이 될지도 모르는" 방어 코드는 가설이고, 가설은 넣지 않는다.

1. 원인. `root-cause` 스킬로 재현하고 처음 잘못된 지점과 메커니즘을 확정한다. 상태가 확정이 아니면 수정으로 넘어가지 않고 멈춰 그 결과를 보고한다.
2. 수정 설계. 처음 잘못된 지점을 고친다(`p-fix-root-causes`). 상태·분기가 얽혀 있으면 형태부터 정한다(`p-model-the-domain`). 증거가 정당화하는 가장 작은 변경. 함수 경계를 넘는 변경이면 대안을 둘 이상 적고 고른 이유를 남긴다.
3. 구현. 실패하는 테스트를 먼저 쓴다(`p-verifiable-units`, `p-test-behavior`). 테스트가 비싸거나 불명확하면 `skip: 이유`와 대체 확인 방법. worker 매핑이 있으면 worker brief로 위임하고 diff를 직접 읽는다. 없으면 owner가 구현한다.
4. 검증. 1단계의 재현이 통과하는지 같은 표면에서 확인한다. 단위 테스트 통과만으로는 결함 부재를 말하지 않는다. "확인 불가"는 통과가 아니다(`p-prove-it-works`).
5. 리뷰. `inspect` 스킬로 점검하고 차단 항목을 처리한다. 의도는 "1단계의 결함이 고쳐지고 다른 동작은 그대로".
6. 커밋 준비. 실패 테스트가 수정보다 먼저 오게 배열한다. 커밋은 사용자 요청이 있을 때.

**멈춤:** 2단계 뒤. 수정 설계는 적기만 하고 구현하지 않는다. 1단계 상태가 확정이 아니면 2단계도 skip한다. 보고는 증상, 재현 조건, 원인 메커니즘과 증거, 수정 설계(처음 잘못된 지점, 영향 범위, 대안), 확인하지 못한 것. 이어 가면 3단계부터.

**보고:** 무엇이 깨졌고, 원인, 수정, 검증 방법. 실패에서 통과로 바뀐 재현 출력을 원문으로 붙인다.
