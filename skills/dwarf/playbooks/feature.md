### Feature

무엇을 어떤 순서로 바꿀지 먼저 정하고, 하위 기능 순서대로 구현한다.

- 관문 대상. 2단계 뒤 판정한다. 설계 요청(설계부터 해줘·설계만·계획 세워 줘)이 있거나, 여러 서브시스템에 걸치거나, 작업 단위가 모두 합쳐 다섯을 넘을 것 같으면. 하위 기능 목록을 담은 스펙을 문서로 쓰고 독립 검토와 사용자 승인을 받은 뒤, 하위 기능마다 구현하고 커밋한다. 사용자는 하위 기능 하나에 커밋 하나로 리뷰한다.
- 관문 대상이 아니면 4·5단계를 `skip: 관문 대상 아님`하고 스펙은 세션에만 둔다. 3단계에서 작업 단위가 다섯을 넘으면 관문 대상으로 바꾸고 4단계로 간다.
- 문서는 `<작업 디렉토리>/.docs/feature/<날짜>-<주제>/spec.md`. `<날짜>`는 `YYYY-MM-DD`, `<주제>`는 영문 kebab-case(예: `2026-10-22-coupon/spec.md`). 작업 디렉토리는 세션을 시작한 디렉토리다. 저장소 루트·상위 디렉토리·스킬 디렉토리에 만들지 않는다. 디렉토리가 없으면 만든다. 형식은 아래. 다른 세션이 문서만 읽고 이어 갈 수 있게 쓰고, 해당 없는 절은 뺀다.
- 문서가 이미 있으면 상태로 이어 갈 단계를 정한다. `spec.md`가 승인 대기면 5단계, 승인됨이면 6단계에서 하위 기능 절의 완료가 아닌 첫 하위 기능부터, 모두 완료면 7단계. 이어 갈 때는 완료 하위 기능의 커밋이 현재 브랜치에 있는지와 남은 변경(`git status`)을 보고, 진행 중 하위 기능은 남은 변경 위에서 이어 간다. 하위 기능 번호를 지정하면 6단계에서 그 하위 기능만 구현하고 7단계는 그 하위 기능의 완료 조건과 테스트 케이스만 확인한다. 의존하는 하위 기능이 완료가 아니면 알리고 묻는다.

1. 요구를 자기 말로 다시 쓴다. 완료 조건을 통과/실패로 판정할 수 있는 문장으로 적고, 완료 조건마다 테스트 케이스(상황 → 기대 결과)를 정상·경계·실패로 적는다. 애매하면 해석을 적고 진행하되, 결과가 크게 달라지는 해석 차이만 묻는다.
2. 영향 범위 파악. 닿는 서브시스템과 기존 구현을 `how` 스킬로, 기존 설계의 이유가 제약이 되면 `why` 스킬로(`p-reuse-first`).
3. 스펙. `blueprint` 스킬을 불러 1단계 완료 조건과 2단계 파악 결과를 넘기고 데이터 형태, 대안 비교표, 하위 기능과 작업 단위, 리스크·미결을 받는다. 작업 단위는 문서에 쓰지 않고 6단계 todo로 쓴다. 한두 파일의 명백한 변경이면 3~5단계를 `skip: 이유`하고 단일 단위로 6단계에 간다. 이때는 관문 대상이 아니고, 설계 요청이 있었으면 6단계 전에 바꿀 곳을 보고하고 문서 없이 진행할지 묻는다.
4. 스펙 검토. 1~3단계 결과를 `spec.md`에 상태 승인 대기로 쓰고 `inspect` 스킬로 문서를 점검한다. 의도는 1단계 요구와 완료 조건. 발견 사항마다 반영하거나 기각 이유를 적어 `spec.md`의 검토 절에 남긴다. 재검토는 사용자가 요청할 때만.
5. 관문 1. 사용자 승인을 기다린다. 보고는 `spec.md` 절대 경로, 완료 조건, 대안 비교표, 하위 기능 목록(순서, 의존), 리스크·미결, 검토 발견 사항과 반영·기각, 구현 때 하위 기능마다 커밋할 현재 브랜치와 이미 있는 변경(`git status`). 수정 요청은 `spec.md`를 고치고(고른 안이 바뀌면 바뀐 안을 넘겨 3단계 `blueprint`를 다시 부른다) 바뀐 곳을 보고한다. 승인되면 `spec.md` 상태를 승인됨과 날짜로 바꾼다. 이 승인이 하위 기능별 커밋 승인이다. 승인 전에는 6단계로 가지 않는다.
6. 구현. 하위 기능을 순서대로. 시작할 때 그 하위 기능의 작업 단위를 todo로 둔다. 3단계 결과가 세션에 없거나(다른 세션에서 이어 갈 때) 관문 1에서 하위 기능이 바뀌었으면 작업 단위를 새로 나눈다(`p-verifiable-units`). 작업 단위별로 그 단위가 맡는 테스트를 먼저 쓰고 의도한 이유로 실패하는지 본 뒤 구현 → 확인 명령 → 다음(`p-test-behavior`). 테스트가 비싸거나 불명확하면 `skip: 이유`와 대체 확인 방법. 끝나면 하위 기능의 완료 조건을 확인하고 `inspect` 스킬로 점검해 차단 항목을 처리한다. 점검 대상은 그 하위 기능이 바꾼 파일의 `git diff`와 새로 만든 파일, 의도는 그 하위 기능의 완료 조건. 앞 하위 기능이 커밋되지 않았으면 겹친 파일은 앞 변경을 이미 점검했다고 함께 넘긴다. 관문 1을 승인받았으면(`spec.md` 승인됨) 시작할 때 하위 기능 절의 상태를 진행 중으로 바꾸고, 점검을 통과하면 그 하위 기능이 만든 변경만 스테이징해 현재 브랜치에 커밋하고(push하지 않는다) 상태를 완료와 커밋 SHA로 바꾼다. `spec.md`와 실행 전부터 있던 변경은 커밋하지 않고, 실행 전부터 있던 변경과 같은 파일이면 커밋 전에 묻는다. 커밋한 하위 기능을 고칠 때는 amend하지 않고 새 커밋으로 한다. 확인이 실패하거나 차단 항목이 남으면 커밋하지 않고 다음 하위 기능으로 가지 않는다. 관문 1을 승인받았으면 상태를 `진행 중 (차단: <요약>)`으로 적는다. 끝낸 하위 기능과 실패 출력 또는 차단 항목을 보고하고, 이어 가면 그 하위 기능부터. 해결에 스펙 변경이 필요하면 `spec.md`를 고쳐 승인 대기로 되돌리고 5단계로 간다. worker 매핑이 있으면 단위별 worker brief(커밋 금지)로 위임하고 diff를 직접 읽는다. 커밋은 owner가 한다.
7. 검증. 1단계의 완료 조건과 테스트 케이스를 실제 표면에서 확인한다. 출력 원문을 남긴다(`p-prove-it-works`). 변경이 diff 밖에 닿으면 `blast-radius` 스킬.
8. 커밋 준비. 관문 1을 승인받았으면 `skip: 6단계에서 커밋함`. 아니면 하위 기능 하나에 커밋 하나로 준비하고(같은 파일을 함께 고쳐 나눌 수 없으면 합치고 보고에 적는다), 커밋은 사용자 요청이 있을 때.

**멈춤:** 5단계 뒤. 멈춤 요청이면 관문 1의 승인은 스펙 확정이고 구현 지시가 아니다. 보고는 5단계 보고. 이어 가면 6단계부터.

**보고:** 만든 것, 선택과 이유(대안 비교표), 하위 기능별 커밋 SHA와 확인·점검 결과, 검증 출력, 남은 결정.

`spec.md` 형식. 완료 조건과 테스트 케이스의 ID는 하위 기능 절이 참조한다.
