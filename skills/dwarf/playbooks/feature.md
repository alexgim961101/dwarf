### Feature

설계를 소유한다. 구현은 설계가 정한 단위대로.

design 문서가 있으면 1~3단계는 그 문서를 쓰고 4단계부터 시작한다. 여러 서브시스템에 걸치거나 단위가 다섯을 넘으면 design을 먼저 제안한다.

1. 요구를 자기 말로 다시 쓴다. 완료 조건을 통과/실패로 판정할 수 있는 문장으로 적는다. 애매하면 해석을 적고 진행하되, 결과가 크게 달라지는 해석 차이만 묻는다.
2. 영향 범위 파악. 닿는 서브시스템과 기존 구현을 `how` 스킬로, 기존 설계의 이유가 제약이 되면 `why` 스킬로(`p-reuse-first`).
3. 설계. `blueprint` 스킬에 1단계 완료 조건과 2단계 파악 결과를 넘겨 데이터 형태, 대안 비교표, 작업 단위를 받는다. 한두 파일의 명백한 변경이면 `skip: 이유`하고 단일 단위로 간다.
4. 구현. 단위마다 구현 → 검증 → 다음. worker 매핑이 있으면 단위별 worker brief로 위임하고 diff를 직접 읽는다.
5. 검증. 1단계의 완료 조건을 실제 표면에서 확인한다. 출력 원문을 남긴다(`p-prove-it-works`). 변경이 diff 밖에 닿으면 `blast-radius` 스킬.
6. 리뷰. `inspect` 스킬로 점검하고 차단 항목을 처리한다. 의도는 1단계 완료 조건.
7. 커밋 준비. 단위 순서대로 작은 커밋. 커밋은 사용자 요청이 있을 때.

**보고:** 만든 것, 선택과 이유(대안 비교표), 검증 출력, 남은 결정.
