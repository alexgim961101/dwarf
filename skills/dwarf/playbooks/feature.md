### Feature

설계를 소유한다. 구현은 설계가 정한 단위대로.

design 문서가 있으면 1~4단계는 그 문서를 쓰고 5단계부터 시작한다. 여러 서브시스템에 걸치거나 단위가 다섯을 넘으면 design을 먼저 제안한다.

1. 요구를 자기 말로 다시 쓴다. 완료 조건을 통과/실패로 판정할 수 있는 문장으로 적는다. 애매하면 해석을 적고 진행하되, 결과가 크게 달라지는 해석 차이만 묻는다.
2. 영향 범위 파악. 닿는 서브시스템을 `how` 스킬로 파악한다(`p-reuse-first`).
3. 설계. 데이터 형태를 먼저 정한다. 상태, 타입, 구조(`p-model-the-domain`, `p-respect-structure`, `p-necessary-only`). 대안이 둘 이상이면 비교표를 쓰고 고른 이유를 남긴다. 한두 파일의 명백한 변경이면 `skip: 이유`.
4. 계획. 검증으로 끝나는 작은 단위로 나눈다(`p-verifiable-units`). 단위마다 확인 명령을 적는다. 단위가 하나면 `skip: 단일 단위`.
5. 구현. 단위마다 구현 → 검증 → 다음. worker 매핑이 있으면 단위별 worker brief로 위임하고 diff를 직접 읽는다.
6. 검증. 1단계의 완료 조건을 실제 표면에서 확인한다. 출력 원문을 남긴다(`p-prove-it-works`). 변경이 diff 밖에 닿으면 `blast-radius` 스킬.
7. 리뷰. reviewer 매핑이 있으면 독립 리뷰. 없으면 owner 재검토를 보고에 적는다.
8. 커밋 준비. 단위 순서대로 작은 커밋. 커밋은 사용자 요청이 있을 때.

**보고:** 만든 것, 선택과 이유(대안 비교표), 검증 출력, 남은 결정.
