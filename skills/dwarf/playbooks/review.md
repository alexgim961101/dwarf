### Review

판정을 소유한다. 읽기 전용. 입력은 diff·브랜치·PR, 산출물은 근거 있는 발견 사항과 판정.

1. 변경의 의도를 한 문장으로 적는다. PR 설명·커밋 메시지·대화에서. 없으면 코드에서 추론하고 추론이라고 표시한다.
2. 변경 범위를 잡는다. `git diff <base>`, 변경 파일 목록, 닿는 호출부. 변경이 닿는 서브시스템을 모르면 `how` 스킬.
3. 의도와 대조한다. 의도와 다른 동작, 회귀 가능성, 빠진 검증, 요구에 없는 변경, 구조 위반(`p-respect-structure`), 불필요한 추가(`p-necessary-only`). 설명 없는 주석, 주석 처리된 코드, 우회를 설명하는 주석은 권고 항목. 회귀가 diff 밖에 있을 수 있으면 `blast-radius` 스킬로 안전의 근거를 증명한다.
4. 발견 사항마다 위치(파일:줄), 문제, 근거 또는 재현, 심각도(차단 / 권고 / 참고)를 적는다. 실행으로 확인할 수 있으면 실행한다(`p-prove-it-works`).
5. reviewer 매핑이 있으면 같은 diff를 reviewer brief로 보내 독립 의견을 받고, 일치·불일치를 표시한다. 없으면 생략하고 보고에 적는다.
6. 판정. 머지 가능 / 수정 필요. 확인했지만 문제 없던 항목도 적는다.

코드 변경 없음. 수정 요청이 붙으면 발견 사항을 입력으로 bug-fix 또는 feature를 제안한다.

**보고:** 의도, 발견 사항 표(위치·문제·근거·심각도), 확인한 항목, 판정.
