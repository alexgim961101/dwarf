### Design

설계를 소유한다. 코드는 쓰지 않는다. 산출물은 설계 문서 또는 계획 문서.

1. 요구를 자기 말로 다시 쓴다. 완료 조건을 통과/실패로 판정할 수 있는 문장으로. 요구가 미정이면 brainstorm을 먼저 제안한다.
2. 영향 범위 파악. 닿는 서브시스템과 기존 구현을 `how` 스킬로, 기존 설계의 이유가 제약이 되면 `why` 스킬로(`p-reuse-first`).
3. 설계. 데이터 형태를 먼저 정한다(`p-model-the-domain`). 대안 2개 이상을 비교표로, 고른 이유와 버린 이유(`p-respect-structure`, `p-necessary-only`).
4. 계획. 검증으로 끝나는 작은 단위로 나눈다(`p-verifiable-units`). 단위마다 바꾸는 파일, 확인 명령, 완료 조건. 순서와 의존.
5. 리스크와 미결. 되돌리기 어려운 지점, 사용자가 정해야 할 것.
6. 문서로 남기고 멈춘다. 실행은 사용자의 승인 뒤 feature 5단계부터. 문서의 단위 분할이 그대로 todo가 된다.

feature 1~4단계와 같고 여기서 멈춘다. 한두 파일의 자명한 변경이면 문서를 만들지 말고 feature를 제안한다.

**보고:** 문서 경로, 완료 조건, 대안 비교표, 단위 분할과 순서, 리스크와 미결.
