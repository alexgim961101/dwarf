### Incident

실행 중인 시스템(서버·컨테이너·클라우드 자원)의 장애를 진단하고 복구한다. 진단은 읽기만으로 한다. 실행 중인 대상의 상태(배포·재시작·reload·설정 반영·스케일·데이터)와 저장소의 설정은 관문 1에서 사용자가 고른 것만, 고른 순서로 바꾼다. 해결은 즉시 완화, 구조적 해결, 재발 방지로 나눠 정한다.

1. 대상과 안전: 먼저 관문을 `status: pending`으로 기록한다(`references/gate.md`). 대상 환경(로컬·스테이징·운영), 구성 요소, 접근 수단(docker, ssh, kubectl, aws 등), 사용자 영향과 그것이 커지고 있는지, 복구됐다고 볼 기준을 적는다.
   - 관문 1 전에는 실행 중인 대상의 상태를 바꾸는 명령을 실행하지 않는다. 배포·재시작·reload·설정 반영·스케일·삭제가 그렇고, 그런 일을 하는 스크립트(`deploy.sh` 등)와 컨테이너 안 명령도 같다. 스크립트는 내용을 읽어 분석하고, 동작을 보려고 실행하지 않는다. hook이 막지 않았다는 것은 허가가 아니다.
   - 쓰는 명령은 로그·상태·설정 조회, `inspect`·`describe`·`get`, 컨테이너 안에서 하는 조회와 요청이다. 비밀 값이 찍히는 출력(환경 변수 전체, `docker inspect` 전체)은 필요한 필드만 골라 본다.
2. 증상 고정: 사용자가 보는 경로로 증상을 직접 재현하고 명령, 출력, 시각을 남긴다. 정상이던 시점과 그 뒤 바뀐 것을 모은다. 커밋과 배포 기록, 실행 중인 이미지·버전, 컨테이너·프로세스 시작 시각, 설정 변경, 인프라 변경.
3. 경로 따라가기: 증상이 지나는 구간을 하나씩 본다. 요청형 서비스는 클라이언트 → 프록시·LB → 서비스 → 의존 서비스, 배치·비동기는 입력 → queue → worker → 출력. 구간마다 받았는지, 무엇을 기록했는지, 무엇을 돌려줬는지, 재시작·종료 사유와 자원 한계를 본다. 앞 구간을 건너뛰고 뒤 구간을 직접 불러 어느 구간부터 틀렸는지 가른다. 직접 부를 때는 원래 요청의 프로토콜·포트·경로·Host를 유지하고 달라진 조건을 적는다.
   - 주소가 걸린 장애면 오류 로그에 찍힌 상대(주소·포트·이름)와, 요청을 보내는 구성 요소 안에서 확인한 이름 해석 결과와 실제로 듣는 대상을 출력으로 나란히 놓는다. 값마다 조회 명령과 시각을 남긴다.
4. 가설 가르기: 2단계의 변경과 3단계의 후보마다, 그것이 원인이라면 무엇이 보여야 하는지 적고 출력으로 확인한다.
   - 최근 커밋은 실행 중인 버전에 실제로 들어갔는지 먼저 확인한다. 최근이라는 이유만으로 원인이나 무관으로 판정하지 않는다. 확인하지 못한 변경은 "미검증"으로 남기고 배제했다고 쓰지 않는다.
   - 오류 종류는 가설을 좁히는 단서이고 원인을 확정하지 않는다. 연결 거절은 듣는 곳이 없거나 명시적으로 거부한 것, 타임아웃은 연결·응답 대기 중 어느 구간인지, 도달 불가는 주소·경로·네트워크 정책, 5xx는 그 응답을 만든 구성 요소와 그 아래 실패를 로그로 확인한다.
   - 원인 상태는 확정 / 유력 / 미확정 중 하나다. "무엇이 언제 바뀌어 어떤 경로로 이 증상이 되는가"를 출력으로 보일 수 있으면 확정이다(`p-fix-root-causes`). 확정이 아니어도 근거 있는 즉시 완화가 있으면 5·6단계로 가서 완화만 제안하고, 구조적 해결은 보류한다.
5. 해결안: 세 갈래는 함께 쓰는 조치다. 세 갈래 모두 보고에 남기고, 필요 없거나 보류하면 이유를 적는다.
   - 즉시 완화: 지금 서비스를 되살린다. reload, 재시작, 롤백, 우회.
   - 구조적 해결: 같은 원인이 다시 증상을 내지 않게 설정·코드·IaC를 바꾼다. 저장소에 남긴다. 후보가 둘 이상이면 비교한다.
   - 재발 방지: 같은 종류의 장애를 막거나 일찍 잡는다. 배포 뒤 확인, 경보, 절차.
   - 조치마다 정확한 명령이나 diff, 영향 범위, 위험, 되돌리는 방법, 확인 신호(대기 시간과 성공 기준), 적용 순서를 적는다.
   - 저장소 변경은 실행 중인 대상에 닿는 명령(reload·재생성·배포)까지 함께 적는다. 정하기 전에 설정이 어떻게 들어가는지(이미지에 포함, volume, 파일 하나만 bind mount) 확인한다. 파일 하나만 bind mount 했으면 파일을 새로 쓸 때 컨테이너가 옛 내용을 계속 볼 수 있다.
   - 구조적 해결은 실행 중인 대상과 포트·volume·DB·외부 서비스·자격 증명을 함께 쓰지 않는 임시 환경(예: 다른 project 이름의 compose 복제본)에서 시험하고, 끝나면 지운다. 격리됐는지 확인할 수 없으면 실행하지 않고 필요한 시험을 관문 1에 적는다.
   - 구조적 해결의 diff와 적용·되돌리기 명령을 `inspect` 스킬로 점검하고 차단 항목을 해결한다. 이때 넘기는 의도는 "장애 원인이 다시 증상을 내지 않고 다른 동작은 그대로다".
6. 관문 1: 사용자 승인을 기다린다. 아래 보고 형식에서 관문 1에 쓰는 내용으로 보고한다. 사용자가 조합을 고르면 관문을 `approved`로 바꾸고 7단계에 간다. 질문, 거절, 추가 조사 요청은 승인이 아니다.
7. 적용: 승인받은 조치만 승인받은 순서로 적용한다. 저장소 변경은 승인된 diff 그대로 하고, 실행 중인 상태에는 5단계에 적은 명령으로 반영한다. 반영한 뒤 저장소의 설정, 배포된 설정, 프로세스가 실제로 쓰는 설정이 같은지 그 안에서 확인한다. 대상이 여러 대면 한 대에 먼저 적용해 성공 기준을 확인한 뒤 나머지에 한다. 적용할 내용이 승인안과 달라지면 멈추고 다시 보고한다.
8. 검증: 2단계의 재현 명령을 사용자가 보는 경로로 다시 실행해 증상이 사라졌는지와 다른 경로가 정상인지 본다(`p-prove-it-works`). 구조적 해결은 원인이 된 사건(재배포, 재시작, 주소 변경 등)을 다시 일으켜도 증상이 나지 않는지 확인한다. 운영 대상에서 그 사건을 다시 일으키는 것은 승인된 계획에 있을 때만 하고, 아니면 임시 환경에서 하거나 못 했다고 적는다. 성공 기준을 채우지 못하면 이어 가는 적용을 멈추고, 승인받은 되돌리는 방법으로 되돌리고 보고한다.
9. 마무리: 최종 diff가 승인안과 같은지 확인하고, 임시 환경을 지운다. 커밋은 사용자가 요청할 때만 한다.

- 사용자가 요청에서 즉시 복구를 허락했으면(예: "일단 살려 놔") 2단계 뒤 허락한 범위의 즉시 완화만 관문 1 전에 한다. 먼저 완화가 지울 증거(로그, 설정, 주소, 프로세스 상태)를 남기고, 하려는 조치와 되돌리는 방법을 적는다. 관문은 `pending`으로 두고 저장소는 바꾸지 않는다. 구조적 해결과 재발 방지는 관문 1에서 따로 승인받는다.
- 원인이 애플리케이션 코드의 결함으로 확정되면 즉시 완화까지만 여기서 정하고, 원인 근거와 남은 영향을 넘겨 bug-fix로 재매칭을 제안한다.

**멈춤:** 관문 1에서 멈춘다. 멈춤 요청이면 승인을 기다리지 않고 관문 1 보고로 마친다. 원인이 미확정이고 근거 있는 완화도 없으면 1~4단계 결과를 보고한다. 이어서 진행하면 고른 조합으로 7단계부터 한다.

**보고:** 아래 형식으로 답한다. 관문 1 보고도 같은 형식이고, 절 이름 옆 표시대로 관문 1과 최종 보고의 내용이 다르다. 이 시스템을 모르는 개발자가 읽어도 흐름을 이해하게 쓴다. 근거는 판정에 필요한 출력 구간만 원문으로 발췌하고 비밀·개인정보는 가린다. 해당 없는 절은 빼되 해결 방법의 세 갈래는 빼지 않는다. 사용자가 요청하면 `<작업 디렉토리>/.docs/incident/<날짜>-<주제>/report.md`에도 쓴다. `<날짜>`는 `YYYY-MM-DD`, `<주제>`는 영문 kebab-case, 작업 디렉토리는 세션을 시작한 디렉토리다.

# 개요
- 증상, 영향(어느 경로, 누가, 언제부터, 커지고 있는지), 대상 환경

# 타임라인
| 시각 | 사건 | 근거 |

# 검증 (최종만)

- 결론을 바꿀 수 있는 것만

# 결정할 것 (관문 1만)
