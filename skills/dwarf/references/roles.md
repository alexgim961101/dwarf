# 역할과 brief 계약

dwarf가 정하는 것은 역할과 brief(위임 지시문)이다. 그 역할을 맡을 Agent는 사용자가 자기 환경에 있는 것 중에서 고르고, 위임할 때의 model·effort도 원하면 함께 고른다(`agents.md`). playbook은 역할 이름만 쓴다.

## 역할

| 역할 | 할 일 | 쓰기 | 기본 Agent (Claude Code) | 매핑이 "없음"일 때 |
|---|---|---|---|---|
| explorer | 대량 읽기·탐색. 파일·흐름·경계를 찾아 포인터로 보고 | 금지 | `Explore` | owner가 직접 읽는다. 한 번에 넓게 읽지 않고 범위를 나눠 읽는다 |
| reviewer | owner가 만든 변경·문서의 독립 리뷰 | 금지 | `general-purpose` | owner가 체크리스트로 재검토하고 보고에 "독립 리뷰 없음"을 적는다 |
| worker | 구현 위임 | 허용 | 없음 | owner가 직접 구현한다 |

## 위임 여부와 Agent

역할을 지정한 단계는 위임하기 전에 정한다.

- 직접. 그 역할의 매핑이 `none`이거나 이번 실행에서 서브에이전트를 쓰지 않기로 했으면(사용자 요청 또는 실행 시작 때의 선택) spawn하지 않는다. 위 표의 "매핑이 '없음'일 때"대로 한다.
- 위임. 매핑에 그 역할로 기록된 Agent를 쓰고 다른 Agent로 바꾸지 않는다. 그 역할의 model·effort 기록이 있으면 위임 호출에 그대로 넘기고, 없으면 넘기지 않는다. 기록된 Agent가 이 세션에 없을 때만 기본값으로 대체하고 답변에 한 줄 적는다. 대체해도 model·effort는 그대로 넘긴다.
- 매핑은 이미 적용된 것이 있으면 그것을 쓴다. leaf 단독 호출이면 `agents.md`의 "어디서 읽나" 순서로 읽고, 기록이 없으면 역할의 기본값을 쓴다.

## 공통 규칙

- 자기완결. Agent가 dwarf의 다른 파일을 읽지 않아도 일이 되게 쓴다.
- 포인터로 넘긴다. 파일 경로·줄 범위·명령을 적고, 긴 내용을 brief에 붙이지 않는다.
- 쓰기 정책을 첫 줄에 쓴다. explorer·reviewer는 "파일을 수정하지 않는다".
- 반환 형식을 지정한다. 아래 역할별 항목.
- brief 하나는 질문 하나, 변경 하나, 또는 함께 보는 문서 묶음 하나.
- 같은 Agent를 이어 쓰지 않는다. 후속 작업은 원래 brief, 추가 지시, 이전 보고를 합친 새 brief로 새 Agent를 띄운다.
- 여러 explorer는 한 메시지에 동시에 띄운다. 각도가 겹치지 않게 범위를 나눈다.
- 결과를 받으면 owner가 확인한다. explorer·reviewer 뒤에는 `git status`로 변경이 없는지 본다. worker 뒤에는 diff를 직접 읽는다.
- 위임 결과를 답변에 그대로 붙이지 않는다. owner가 자기 말로 요약하고, 근거가 필요한 부분만 인용한다.

## explorer brief

```
파일을 수정하지 않는다.
질문: <한 문장>
범위: <디렉토리·파일·심볼. 다른 explorer가 맡은 범위는 보지 않는다>
제약: <선택. 제외할 자료, 시간 범위. 없으면 줄을 뺀다>
반환:
- 구성 요소: 이름, 경로, 한 줄 설명
- 흐름: 진입점(무엇이 시작시키나)부터 단계별로 함수 → 파일 → 다음 호출, 넘어가는 데이터, 분기 지점과 조건, 단계의 의미 한 줄(무엇을 하려는 호출인지). API 경로·함수·파일 경로는 원문 그대로
- 경계: 다른 서브시스템과 닿는 입력·출력
- 읽은 파일 전체 목록
- 뜻밖의 것: 보기와 다르게 동작하는 부분
- 미확인: 끝까지 따라가지 못한 것
```

## reviewer brief

```
파일을 수정하지 않는다.
변경: <브랜치, 커밋 범위, 또는 `git diff <base>` 명령>
의도: <변경 목적과 완료 기준. owner가 한 문장으로>
중심 질문: <선택. 이 변경에서 특히 확인할 것. 없으면 줄을 뺀다>
확인할 것: 의도와 다른 동작, 회귀 가능성, 빠진 검증, 요구에 없는 변경
반환:
- 발견 사항마다: 위치(파일:줄), 문제, 재현 또는 근거, 심각도(차단 / 권고 / 참고)
- 확인했지만 문제 없던 항목
- 판정: 머지 가능 / 수정 필요
```

## reviewer brief (문서)

```
파일을 수정하지 않는다.
문서: <설계·계획 문서 경로. 함께 보는 문서는 전부>
의도: <요구와 완료 조건. owner가 한두 문장으로>
중심 질문: <선택. 이 문서에서 특히 확인할 것. 없으면 줄을 뺀다>
확인할 것: 빠진 요구, 판정할 수 없는 완료 조건, 테스트 케이스가 없는 완료 조건과 빠진 경계·실패 케이스, 문서의 파일:줄·동작 주장이 코드와 맞는지(직접 열어 확인), 빠진 대안과 고른 이유, 빠진 리스크(스키마·공개 API·데이터), 요구에 없는 작업. 계획 문서면 완료 조건과 테스트 케이스가 하위 기능에 빠짐없이 나뉘었는지, 테스트가 내부 구현이 아니라 관찰 가능한 결과를 확인하는지, 하위 기능마다 혼자 확인할 수 있는지, 의존 순서, 하위 기능끼리 같은 파일을 고쳐 부딪히는지, 작업 단위마다 확인 명령이 있는지
반환:
- 발견 사항마다: 위치(문서 경로와 절, 또는 파일:줄), 문제, 근거, 심각도(차단 / 권고 / 참고)
- 확인했지만 문제 없던 항목
- 판정: 승인 가능 / 수정 필요
```

## worker brief

```
범위: <수정 가능한 파일 목록. 그 밖은 수정하지 않는다>
목표: <한 문장>
확정된 사실: <owner가 확인한 원인·설계. 다시 조사하지 않는다>
데이터 형태: <먼저 정할 상태·타입·구조>
완료 기준: <통과해야 하는 명령과 기대 출력>
커밋: <단위와 순서. 예: 실패 테스트 먼저, 수정 다음. 커밋 금지면 그렇게>
반환: 변경 파일, 커밋 SHA(있으면), 검증 명령의 출력 원문
```
