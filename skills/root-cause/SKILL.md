# root-cause

결함이 왜 일어나는지 증거를 들어 답한다. 결과물은 재현 방법과 결함이 생기는 과정이고, 코드는 고치지 않는다. 코드를 읽고 짐작한 원인은 아직 가설이며, 실행해서 얻은 증거가 있어야 확정한다.

## 입력

- 증상: 에러 메시지, 로그, 실제로 본 잘못된 동작.
- 증상이 나타난 곳: API, UI, 배치, 테스트 중 어디에서 보였는지.
- 정상이던 시점: 회귀일 때만. 마지막으로 정상 동작한 날짜나 커밋.

## 절차

1. 재현: 증상이 나타난 곳을 owner가 직접 구동해 재현한다.
   - 곳마다 수단: API는 HTTP 요청, CLI는 명령, 배치는 작은 입력으로 실행, 테스트는 그 테스트만, UI는 브라우저 자동화.
   - UI는 세션의 브라우저 도구로 먼저 살펴보더라도, 재현은 다시 돌릴 수 있는 스크립트(예: Playwright)로 남긴다. 스크린샷, 콘솔 로그, 네트워크 요청을 증거로 남긴다.
   - 재현 스크립트는 작업 트리 밖 임시 디렉토리에 두고 경로를 출력에 적는다. 이 스크립트가 재현 명령이고, 고친 뒤 확인할 때 다시 돌리므로 6단계에서 지우지 않는다.
   - 바로 재현되지 않으면 조건을 좁히거나, 그 상태를 테스트 데이터나 스크립트로 직접 만들거나, 로그나 임시 코드를 넣어 값을 찍어 본다.
   - 사용자에게 재현을 넘기지 않는다. 도구가 닿지 않는 구체적 이유(2단계 인증, 실기기 등)가 있을 때만, 갈 수 있는 데까지 간 뒤에 넘긴다.
   - 도구가 없으면 전역 설치 없이 실행하고(`npx`), 작업 트리와 lockfile은 바꾸지 않는다. 브라우저 내려받기처럼 전역에 남는 것은 먼저 묻는다.
   - 가끔만 일어나면 여러 번 실행해 몇 번 중 몇 번 일어나는지 적는다. 끝내 재현되지 않으면 시도한 조건을 남기고 상태를 "재현 불가"로 마친다.
2. 가설 세우기: 관련 코드가 어떻게 동작하는지 모르면 먼저 `how`로 파악한다. 회귀면 정상이던 시점 이후 관련 파일의 변경 이력(`git log`)을 보고 바뀐 곳을 가설에 넣는다. 바뀐 이유를 알아야 가설을 가를 수 있으면 `why`로 확인한다. 가설마다 그 가설이 맞다면 실행했을 때 무엇이 보여야 하는지 적는다.
3. 가설 지우기: 실행 결과, 로그, 디버거로 확인해 하나씩 지운다. 확인하기 쉬우면서 한 번에 많은 가설을 가르는 확인부터 한다. 예를 들어 값이 지나가는 경로 중간에서 값을 찍으면 그 앞과 뒤 중 어디서 잘못됐는지 한 번에 가를 수 있다. 지운 가설은 왜 지웠는지와 함께 남긴다.
4. 결함이 들어온 커밋 찾기: 회귀일 때만 한다. `git bisect`로 찾고, 커밋마다 정상인지 가르는 명령으로 1단계의 재현 명령을 쓴다. 찾은 커밋을 왜 만들었는지는 `why`로 확인한다.
5. 원인 확정: 남은 가설을 "이 값이 여기서 이렇게 들어와서 저기서 이렇게 된다"처럼 파일:줄과 실행 출력으로 보인다. 문제가 처음 시작된 곳을 짚는다. 증상이 나타난 곳과 다를 수 있다(`p-fix-root-causes`). 같은 잘못이 다른 곳에도 있는지 찾는다. 같은 함수를 부르는 다른 곳, 복사해 쓴 코드, 같은 가정을 한 코드를 본다.
6. 임시 코드 지우기: 넣은 로그와 임시 코드를 지우고 `git status`로 남은 변경이 없는지 본다. 작업 트리 밖의 재현 스크립트는 남긴다.

## 출력 형식

- **상태:** 확정 / 재현 불가 / 원인 미확정.
- **재현:** 실행한 명령(재현 스크립트면 그 경로), 입력, 출력 원문. UI는 스크린샷과 콘솔 로그 경로도. 가끔만 일어나면 몇 번 중 몇 번인지. 재현하지 못했으면 시도한 조건.
- **지운 가설:** 가설마다 지운 근거.
- **결함이 생기는 과정:** 문제가 처음 시작된 곳(파일:줄), 값이 흘러간 경로, 증거가 된 출력.
- **같은 결함이 있는 다른 곳:** 파일:줄과 근거. 없으면 어떻게 찾았는지.
- **결함이 들어온 커밋:** 회귀일 때만. 커밋과 그 커밋을 만든 이유.
- **확인하지 못한 것:** 무엇을 왜 확인하지 못했는지.

## 경계

- 코드는 고치지 않는다. 로그와 임시 코드는 원인을 보려고 잠시 넣는 것이고 6단계에서 지운다.
- 재현하지 못하면 원인을 확정하지 않는다. "재현 불가" 상태로 마친다.
- 느리거나 자원을 많이 쓰는 문제의 병목을 측정으로 찾는 일은 `bench`가 맡는다.
