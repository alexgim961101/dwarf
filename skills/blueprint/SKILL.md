# blueprint

정해진 요구를 무엇을 어떤 순서로 바꿀지로 옮긴다. 산출물은 데이터 형태, 고른 안과 이유, 하위 기능과 작업 단위 목록. 코드는 쓰지 않는다.

## 입력

- 완료 조건. 통과/실패로 판정할 수 있는 문장. 판정할 수 없으면 판정 가능한 문장으로 고쳐 쓰고 그 해석을 미결에 적는다. 테스트 케이스(상황 → 기대 결과)가 있으면 함께.
- 파악 결과. 닿는 서브시스템, 재사용할 기존 구현, 지켜야 할 기존 설계의 이유. 없으면 1단계에서 만든다.
- 선택. 정해진 안. 사용자가 고른 안이 있으면 3단계 비교에서 그 안을 고르고, 고른 이유에 사용자 결정이라고 적는다.

## 절차

1. 파악 결과가 없으면 만든다. 닿는 코드는 `how`, 지금 모양의 이유가 제약이 될 것 같으면 `why`. 같은 책임의 기존 구현을 먼저 찾는다(`p-reuse-first`).
2. 데이터 형태를 정한다. 상태, 타입, 구조. 분기가 늘 것 같으면 조건문 대신 형태에 담는다(`p-model-the-domain`).
3. 대안을 비교한다. 구조가 다른 안 둘 이상을 효과·비용·리스크·버리는 것으로 표에 놓고 하나를 고른다. 고른 이유와 버린 이유를 적는다. 실질적인 대안이 하나뿐이면 왜 그런지 적는다(`p-respect-structure`, `p-necessary-only`).
4. 하위 기능으로 나누고, 하위 기능마다 작업 단위로 나눈다(`p-verifiable-units`).
   - 하위 기능은 혼자 동작을 확인할 수 있는 조각이다. 계층별(저장소 → API → 화면)로 나누면 혼자 확인할 수 없어 피한다. 하위 기능마다 맡는 완료 조건과 테스트 케이스, 테스트 위치와 수준(단위·통합·e2e), 앞선 하위 기능과의 의존. 모든 완료 조건과 테스트 케이스가 어느 하위 기능엔가 속한다. 테스트는 관찰 가능한 결과를 확인한다(`p-test-behavior`). 작으면 하위 기능 하나.
   - 작업 단위마다 바꾸는 파일, 확인 명령, 완료 조건, 앞선 단위와의 의존. 각 단위는 검증으로 끝난다.
5. 리스크와 미결을 적는다. 되돌리기 어려운 지점(스키마, 공개 API, 데이터), 사용자가 정해야 할 것.

## 출력 형식

- **데이터 형태.** 상태·타입·구조.
- **대안 비교표.** 안, 효과, 비용, 리스크, 버리는 것. 고른 안과 이유.
- **하위 기능.** 순서대로. 하위 기능마다 완료 조건, 테스트(케이스, 위치, 수준, 확인하는 것), 의존, 작업 단위(파일, 확인 명령, 완료 조건, 의존).
- **리스크·미결.** 되돌리기 어려운 지점, 사용자 결정이 필요한 것.

## 경계

- 코드를 쓰지 않는다. 결과를 문서로 남길지, 어디에 남길지는 부르는 쪽이 정한다.
- 무엇을 할지 자체가 미정이면 설계하지 않는다. 미정인 점을 리스크·미결에 적어 돌려준다.
