# how

코드베이스를 읽어 "X는 어떻게 동작하나"에 답한다. 독자는 이 서브시스템에 새로 합류한 시니어 엔지니어. 쓸 수 있는 멘탈 모델이 잡힐 만큼 쓰고, 소스를 한 줄씩 해설하지 않는다. 코드 변경 없음.

## 절차

1. 질문을 한 문장으로 다시 쓴다. 범위가 애매하면 해석을 적고 진행한다. 사용자가 고칠 수 있다.
2. 복잡도를 판정한다.
   - 단순. 모듈 하나, 작은 유틸, "함수 X는 어떻게 동작하나" 같은 좁은 질문. owner가 직접 읽고 4로 간다. spawn 없음.
   - 복잡. 여러 파일·서비스에 걸친 서브시스템, 횡단 기능, 전체 구조 개요. 3으로 간다.
   - 애매하면 단순으로 간다.
3. 질문을 2~4개 각도로 나눈다. 각도는 서브시스템의 서로 다른 조각이어야 하고 겹치지 않는다. 각도마다 explorer 하나를 `../dwarf/references/roles.md`의 explorer brief로, 한 메시지에 동시에 보낸다(`p-guard-context`). explorer 매핑이 없으면 owner가 각도 순서대로 직접 읽되 한 각도를 끝내고 다음으로 간다.
4. owner가 종합한다. explorer 보고를 그대로 붙이지 않고 아래 형식으로 다시 쓴다. 보고 사이에 모순이 있으면 해당 파일을 직접 열어 확인한다. 모순이 없어도 답의 뼈대가 되는 연결(진입점, 핵심 분기, 서브시스템 경계를 넘는 호출)이 보고 하나에서만 나왔으면 직접 열어 확인한다(`p-prove-it-works`). 확인하지 못한 연결은 주의점에 미확인으로 남긴다.
5. explorer를 썼으면 `git status`로 변경이 없는지 본다.

## 출력 형식

해당 없는 절은 뺀다. 모든 주장에 파일:줄 또는 심볼을 붙인다.

구체적인 이름으로 쓴다. "`OrderService`가 `PaymentClient.charge()`를 부른다"이지 "서비스가 클라이언트에 위임한다"가 아니다. 의사코드로 바꿔 쓰지 않고, 코드는 요점을 보이는 데 꼭 필요한 몇 줄만 인용한다.

- **개요.** 이 서브시스템이 무엇을 하고 어디에 끼어 있는지 두세 문장.
- **핵심 개념.** 알아야 하는 타입·서비스·추상화. 이름, 경로, 한 줄 설명.
- **동작 방식.** 가장 긴 절. 무엇이 시작시키는지(요청, 이벤트, 스케줄, 호출부)부터 단계로 따라간다. 단계마다 어느 함수가 어느 파일에서 무엇을 하고 다음에 무엇을 부르는지, 사이에 흐르는 데이터, 흐름이 갈리는 분기 지점과 조건.
  - 여러 구성 요소가 주고받거나 데이터가 단계를 거치며 바뀌면 코드 블록 안 텍스트 다이어그램을 붙인다. 노드는 함수(파일:줄), 화살표에는 오가는 데이터. 글로 충분하면 그리지 않는다.
- **코드 위치.** 무엇을 바꾸려면 어디를 보는지. 경계와 입출력.
- **주의점.** 보기와 다르게 동작하는 것, 역사적 이유가 있는 것, 틀리기 쉬운 것. explorer가 끝까지 따라가지 못한 것은 미확인으로 표시.

## 경계

- "왜 이렇게 만들었나"는 `why`. how가 그 질문을 만나면 사실만 적고 동기는 why를 제안한다.
- 설명 도중 결함을 발견하면 주의점에 적고 수정하지 않는다. 결함의 원인 조사는 `root-cause`.
